# UI and Backend Run Model

This project should treat uploaded FASTQ data and analysis runs as separate concepts.

## Core Entities

### Dataset

A dataset is created when the user uploads FASTQ files once.

Store:

```text
dataset_id
user_id
project_id
created_at
upload_root
samplesheet_path
sample_count
samples
fastq_files
file_sizes
checksums
organism
platform
library_layout
```

The sample sheet is the reusable input contract for all future runs:

```csv
sample_id,library_layout,fastq_1,fastq_2,platform
sample1,paired,uploads/dataset001/sample1_R1.fastq.gz,uploads/dataset001/sample1_R2.fastq.gz,illumina
```

### Run Request

A run request is created each time the user clicks Run.

Store:

```text
run_id
dataset_id
user_id
run_type: single_step | workflow_chain
omics
selected_steps
input samplesheet
outdir
params
execution_profile
created_at
```

One uploaded dataset can have many run requests:

```text
dataset001
  -> run001: FastQC only
  -> run002: trimming only
  -> run003: FastQC + trimming
  -> run004: future alignment/quantification workflow
```

### Compiled Run

Compilation creates a reproducible run bundle:

```text
workflows/generated/<run_id>/
  main.nf
  nextflow.config
  params.yaml
  workflow_manifest.json
  ui_run_summary.json
  methods.md
  run_command.sh
```

These files are now generated by the compiler.

### Execution Record

Execution starts when Nextflow is launched.

Store:

```text
run_id
status: queued | running | succeeded | failed | cancelled
nextflow_command
started_at
finished_at
return_code
stdout_path
stderr_path
nextflow_log_path
work_dir
results_dir
process_statuses
output_files
```

## UI Behavior

### Upload Page

The user uploads FASTQ files once. The backend creates:

```text
uploads/<dataset_id>/
  samplesheet.csv
  fastq/
```

The UI should show:

```text
sample count
paired/single layout
FASTQ filenames
file sizes
ready-to-run status
```

### Step Builder Page

The UI reads `registry/steps.yaml`.

For each selected step, show:

```text
step_name
purpose
tool
user/expert parameters
expected outputs
recommended next steps
```

The user can choose:

```text
single step: FastQC only
single step: trimming only
workflow chain: FastQC + trimming
```

The backend should set:

```text
run_type = single_step       when selected_steps length is 1
run_type = workflow_chain    when selected_steps length is greater than 1
```

### Run Detail Page

Use `ui_run_summary.json` first. It is designed for display.

Show tabs:

```text
Overview
Inputs
One tab per selected step
Methods
Logs
Files
```

For a single-step run, the page still looks the same but has only one step tab.

For a workflow-chain run, each process gets its own step tab.

## What to Save for Results Display

For every run, keep:

```text
workflow_manifest.json
ui_run_summary.json
methods.md
run_command.sh
.nextflow.log
results/<run_id>/**
work directory process logs if failed
```

For each step tab, display files matching that step's registry outputs:

```text
FASTQC:
  03_raw_qc/fastqc/*_fastqc.html
  03_raw_qc/fastqc/*_fastqc.zip

FASTP:
  04_trimmed/*.fastp.html
  04_trimmed/*.fastp.json
  04_trimmed/*.trimmed.fastq.gz
  04_trimmed/trimmed_fastq_manifest.tsv
```

## Backend Flow

1. User uploads FASTQ files.
2. Backend creates a dataset and sample sheet.
3. User selects one step or multiple steps.
4. Backend creates a run request YAML.
5. Builder compiles the run.
6. Backend stores compiled run files.
7. Backend launches `run_command.sh`.
8. Backend tracks status and process logs.
9. Backend collects output files into `execution_record.json`.
10. UI reads `ui_run_summary.json`, `methods.md`, `execution_record.json`, and output files.

## Command Examples

Single step:

```bash
python3 -m builder.api compile \
  --request examples/rnaseq_qc_only_ggal.run.yaml \
  --output workflows/generated/ggal_qc_only_test

bash workflows/generated/ggal_qc_only_test/run_command.sh

python3 -m builder.api collect-outputs \
  --compiled-dir workflows/generated/ggal_qc_only_test \
  --status succeeded
```

Queue-style worker job:

```json
{
  "job_id": "job_ggal_fastqc_only",
  "run_id": "ggal_qc_only_test",
  "compiled_dir": "workflows/generated/ggal_qc_only_test",
  "command": "bash workflows/generated/ggal_qc_only_test/run_command.sh",
  "results_dir": "results/ggal_qc_only_test",
  "execution_profile": "local",
  "logs_dir": "workflows/generated/ggal_qc_only_test/logs"
}
```

Worker command:

```bash
python3 -m builder.api run-job --job jobs/job_ggal_fastqc_only.json
```

This writes:

```text
workflows/generated/ggal_qc_only_test/job_record.json
workflows/generated/ggal_qc_only_test/execution_record.json
workflows/generated/ggal_qc_only_test/logs/stdout.log
workflows/generated/ggal_qc_only_test/logs/stderr.log
```

Workflow chain:

```bash
python3 -m builder.api compile \
  --request examples/rnaseq_qc_trim_ggal.run.yaml \
  --output workflows/generated/ggal_qc_trim_test

bash workflows/generated/ggal_qc_trim_test/run_command.sh

python3 -m builder.api collect-outputs \
  --compiled-dir workflows/generated/ggal_qc_trim_test \
  --status succeeded
```

## Product Decision

Do not treat "single step" and "full workflow" as different systems.

Treat both as the same run object with different `selected_steps`.

The only difference is:

```text
single_step: selected_steps has one item
workflow_chain: selected_steps has two or more items
```

This keeps UI, backend, provenance, logs, and results handling consistent.
